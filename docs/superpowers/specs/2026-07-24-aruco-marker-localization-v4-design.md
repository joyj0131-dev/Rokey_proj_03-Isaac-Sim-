# ArUco 마커 측위·주행 설계 (v4 주차장, 로봇 4대)

> 작성: 2026-07-24
> 대상 환경: `isaacpjt/Isaac_envo/parking/parking_environment_v4.usd`
> 선행 문서: `HANDOFF.md`, `DEBUG_LOG.md`, `ARUCO_PLAN.md`

---

## 1. 목표와 범위

v4 주차장에서 **GT(ground truth)를 제어 입력에서 제거하고, ArUco 바닥 마커로 측위·자세정렬하여
주행**한다. 로봇 4대를 두 팀으로 나눠 입차·출차 프로세스를 동시에 시연한다.

**SLAM은 하지 않는다.** 따라서 마커는 임시 부트스트랩이 아니라 **영구적이고 유일한 절대 위치
기준**이다. 이 전제가 마커 밀도·카메라 사양 판단의 근거가 된다.

### 하는 것

- Isaac 러너가 로봇 카메라 영상(`image_raw`, `camera_info`)과 **휠 엔코더 기반** `odom` 발행
- 순수 ROS 2 노드가 마커 검출 → 월드 측위 → 오도메트리 융합
- 마커 웨이포인트를 따라가는 폐루프 주행과 목표 지점 자세정렬
- 로봇 4대 = 입차팀 2대 + 출차팀 2대, 동시 진행

### 하지 않는 것

- `parking_robot_system` 미션 웨이포인트 좌표의 v4 이식 (별도 작업)
- 차량 리프트·운반 물리
- SLAM / nav2 백엔드

## 2. 좌표 규약 — 에셋 라벨과 반대다

**사용자 기준: 입차 = z 양수, 출차 = z 음수.**

v4 에셋은 정반대로 라벨링되어 있다. `EntryVehicleWait`에 `parking:center = (-8.5, 0, -5.5)`,
`parking:direction = "inbound"`, `parking:displayLabel = "입차 차량 대기 구역"`이 박혀 있어
**에셋은 "입차 = z 음수"라고 명시**한다. 마커 `serves` 값(`W_IN`, `D_IN_1` 등)도 같은 규약이다.

우리는 사용자 기준을 채택하므로, 이 반전을 **`site_map_v4.py` 모듈 한 곳에만** 가둔다.
다른 코드는 `ENTRY` / `EXIT`만 알고 z 부호나 에셋 라벨을 직접 참조하지 않는다.

| 우리 프로세스 | z | 에셋 라벨 | 마커 (id) |
|---|---|---|---|
| **ENTRY (입차)** | z + | `OUT` / Exit | `GATE_OUT`(41), `W_OUT`(51), `D_OUT_1`(21), `D_OUT_2`(23), `XN`(31), `A1'`(3), `A2'`(4), `A3'`(5) |
| **EXIT (출차)** | z − | `IN` / Entry | `GATE_IN`(40), `W_IN`(50), `D_IN_1`(20), `D_IN_2`(22), `XS`(30), `A1`(0), `A2`(1), `A3`(2) |

물리적 주차면 A1~A3은 **z=0 중앙**(x = 2.8 / 6.2 / 9.6)에 있고 양쪽 z=±6.875가 통로다.
입차·출차가 같은 슬롯을 반대편 통로에서 접근하는 구조이므로 반전해도 기하학적으로 성립한다.

> 팀원이 하루 사이 v2→v3→v4를 냈다. 앞으로도 에셋 라벨은 계속 우리와 반대로 말할 것이다.
> 반전을 한 곳에 가두는 것이 이 설계에서 타협 불가한 항목이다.

## 3. GT 사용 규칙

| 용도 | GT | 근거 |
|---|---|---|
| 로봇이 어디로 갈지 결정 (제어 입력) | **금지** | 마커 + 휠 오도메트리만 사용 |
| 측위가 얼마나 틀렸는지 채점 (계측 기준) | **허용** | 진리값이 없으면 오차를 측정할 방법 자체가 없다 |

**조용한 GT 폴백을 금지한다.** 마커를 놓치면 실패로 보고한다.
이 프로젝트에는 폴백이 실패를 통과시킨 전례가 있다 — B5_Pickup이 리프트 0.4 mm, 추종률 0.033
인데도 유도 폴백이 차를 대신 옮겨 `DEMO_PASSED=True`로 찍혔다(`DEBUG_LOG.md` 2026-07-20 밤).
따라서 모든 E2E 테스트는 `markers_used > 0`과 `gt_used_for_control == False`를 합격 조건에 넣는다.

## 4. 아키텍처

무거운 영상은 **C++ OmniGraph 브리지**로 내보낸다. Python rclpy로 이미지를 퍼블리시하면 Isaac
루프가 죽는다(`ARUCO_PLAN.md` 전제). Isaac은 렌더링만 하고 인식 부하를 지지 않는다.

```
Isaac Sim (Python 3.11) — 러너 1개              순수 ROS 2 Humble (3.10)
┌────────────────────────────────┐
│ 로봇 4대 spawn                  │  /robot_<id>/image_raw    ┌────────────────────────┐
│  entry_lead   entry_follow     │  /robot_<id>/camera_info ─▶│ marker_localizer ×N    │
│  exit_lead    exit_follow      │ ────────────────────────  │  검출 + 월드측위 + 융합  │
│                                │  /robot_<id>/odom (휠)     └───────┬────────────────┘
│ OmniGraph (C++)                │ ────────────────────────          │ /robot_<id>/robot_pose
│  ├ ROS2CameraHelper            │                                   │ (+ fix_age)
│  ├ ROS2CameraInfoHelper        │                                   ▼
│  └ ROS2SubscribeTwist  ◀───────┼── /robot_<id>/cmd_vel ── aruco_navigator ×2 (팀 리드)
└────────────────────────────────┘                          + gap_hold (팔로워)
```

### 러너

로봇 4대와 새 토픽 이름 체계는 기존 러너(`dock_lift_handoff_runner_v2.py`, 로봇 2대·
`robot_rear`/`robot_front`)와 호환되지 않는다. 기존 러너를 개조하지 않고 **v4 전용 러너를 새로
만든다.** 검증된 2대 구성이 계속 돌아가야 비교 기준이 남는다.

### 로봇 ID

`entry_lead`, `entry_follow`, `exit_lead`, `exit_follow`.

팀(입차·출차)과 주행 역할(리드·팔로워)이 이름에 드러난다. 리프트 시점의 **차축 담당(앞축/뒷축)은
별도 속성**으로 둔다 — 기존 `rear`/`front` 명명은 축 담당을 뜻해서 팀 구분과 섞이면 혼란해진다.

### v4 로봇 도크

| 도크 | 좌표 | 마커 | 우리 팀 |
|---|---|---|---|
| `ExitRobotDock1` | (-3.2, 0, +2.2) | `D_OUT_1` (21) | entry_lead |
| `ExitRobotDock2` | (-1.2, 0, +2.2) | `D_OUT_2` (23) | entry_follow |
| `EntryRobotDock1` | (-3.2, 0, -2.2) | `D_IN_1` (20) | exit_lead |
| `EntryRobotDock2` | (-1.2, 0, -2.2) | `D_IN_2` (22) | exit_follow |

(에셋 이름의 Entry/Exit와 우리 팀 배정이 반대인 것은 2절 규약에 따른 의도된 결과다.)

## 5. Phase 0 — 측정 (GUI 관찰형)

세 가지 판단(카메라 높이 / 마커 밀도 / 카메라 대수)을 추측이 아니라 **실측 후 사용자가 직접 보고**
결정한다. 따라서 probe는 리포트 생성 배치가 아니라 **GUI로 관찰 가능한 시연**으로 만든다.

세 probe 모두 `--gui`와 `--headless`를 지원하고, JSON 리포트를 남긴다.

### Probe A — 검출 창 (카메라 높이 결정)

로봇을 마커 앞 거리를 바꿔가며 세우고 각 지점에서 잠시 정지해 검출 여부를 보여준다.

- 측정점마다 정지(기본 3초, `--hold-sec`로 조정) — 뷰포트를 돌려 볼 시간 확보
- 바닥 측정점 표식을 **검출 성공=초록 / 실패=빨강**으로 칠함
- 스윕 종료 후 **검출 가능 구간을 바닥 띠(band)로 표시** → "이 로봇은 앞 d_min~d_max 밴드에서만
  마커를 본다"가 한눈에 보임
- 카메라 높이 `{0.09, 0.12, 0.15}` m를 순차 실행 → 띠가 넓어지는 것을 눈으로 비교
- 검출 코너를 그린 이미지 PNG 저장

**산출**: 높이별 `[d_min, d_max]`와 창 폭

기준선: 현재 카메라는 로봇 로컬 x=0.924, **높이 0.090 m, 하향 30°**이고, v1 실측 검출 창은
**앞 1.1~1.4 m (폭 0.30 m)** 였다(`DEBUG_LOG.md` 2026-07-20 심야).

### Probe B — 오도메트리 드리프트 (마커 밀도 결정)

마커 없이 알려진 경로를 주행하며 **두 궤적을 바닥에 동시에 그린다**.

- **흰 선** = GT 실제 경로
- **노란 선** = 휠 오도메트리가 믿는 경로

두 선이 벌어지는 폭이 곧 드리프트다. 끝점에 오차 수치를 텍스트로 표시한다.

**산출**: 거리당 드리프트 % (전진 / 횡이동 각각)

기준선: v1에서 메카넘 휠 오도메트리는 롤러 슬립으로 17 m 주행에 9 m가 어긋났다. 자체 측정
오차는 3~12%였다.

### Probe C — 렌더 부하 (카메라 대수 결정)

카메라 `{0, 2, 4}`대 구성으로 각각 띄워 RTF를 화면에 표시한다.

**산출**: 카메라 대수별 RTF

기준선: 로봇 2대·카메라 0대에서 RTF가 이미 **0.305~0.362**(유휴), **0.251~0.283**(접촉 운반)이다.

팀당 리드 1대만 카메라를 두는 구성(총 2대)이 가능한 이유는, 편대에서 절대측위가 필요한 것은
리드뿐이고 팔로워는 gap-hold로 따라붙기 때문이다.

### 결정 규칙 (미리 못 박음)

```
최장 무마커 구간 거리 × 드리프트율  <  검출 창 폭 × 0.5
```

만족하지 못하면 **카메라를 올리거나 마커를 추가한다.** 어느 쪽인지는 Probe A·B 숫자가 정한다.
안전계수 0.5는 드리프트가 고정 편향이 아니라 분산이라 최악값을 봐야 하기 때문이다.

### v4의 무마커 구간 (사전 계산)

| 구간 | 거리 | 비고 |
|---|---|---|
| 도크 → 인계장 (`D_OUT_1`→`W_OUT`) | 대각 **약 7.2 m** | Δx=-5.3, Δz=+4.875 |
| 인계장 → 크로싱 (`W_OUT`→`XN`) | **6.0 m** | 통로 진입부 |
| 크로싱 → A1' | 5.3 m | |
| A1'→A2'→A3' | 각 3.4 m | 슬롯 간격 |

드리프트 3~12%를 7.2 m에 적용하면 **0.22~0.86 m**다. 검출 창이 0.30 m라면 놓칠 가능성이 높다.
**Probe 결과가 "마커 추가 필요"로 나올 가능성이 크다**고 예상하나, 판단은 실측 후에 한다.

## 6. Phase 1 — 지도 생성

`marker_map_v4.json`을 **v4 USD에서 스크립트가 직접 읽어** 생성한다. 손으로 좌표를 옮겨 적지
않는다 — 이 프로젝트는 이미 인계장 마커가 옛 좌표로 남아 환경과 어긋난 값을 치렀다.

- 입력: v4 USD의 `aruco:markerId`, `aruco:position`, `aruco:yaw`, `aruco:kind`, `aruco:serves`,
  `aruco:codeSize`, `aruco:dictionary`
- 출력: 기존 `marker_map.json` 스키마 + **`role` 필드(ENTRY/EXIT)** 추가. 원본 `serves`는 보존해
  z 반전을 사후 검증할 수 있게 한다
- 사전 `DICT_5X5_100`, `code_size_m = 0.19444445`

> `code_size_m`(코드 크기)와 타일 크기를 혼동하면 거리가 9/7 = 1.286배로 어긋난다.
> 거리 오차가 일정 비율로 나오면 이 값을 가장 먼저 의심할 것.

Probe 결과가 마커 추가를 요구하면, 기존 체계(사전·ID 블록·0.25 m 타일)를 이어서 좌표와 ID를
정해 보강한다.

## 7. Phase 2 — 측위

로봇당 `marker_localizer_node` 하나(카메라 장착 로봇에 한함).

- 입력: `/robot_<id>/image_raw`, `/camera_info`, `/odom`(휠)
- 출력: `/robot_<id>/robot_pose`, 그리고 **`fix_age`(마지막 마커 보정 이후 경과)**
- 기존 자산 재사용: `aruco_pose.py`(합성 자세복원 8/8 통과), `marker_localizer.py`(v1 실제 렌더
  단일 측위 오차 0.6 cm / 0.3°)
- 상보필터: 휠 오도로 예측, 마커로 보정
- **재투영 오차 3.0 px 초과 fix는 기각**(기존 노드 기본값과 동일). 오검출로 로봇이 엉뚱한
  좌표로 순간이동하는 것이 최악의 실패 모드다. v1 실측에서 정상 검출은 대부분 1 px 미만이었다
- `fix_age`를 발행하는 이유: 컨트롤러가 "얼마나 오래 눈을 감고 달렸는지" 알아야 눈감고 주행하는
  것을 거부할 수 있다

### M5 정확도 관문

여러 자세를 스윕해 측위 오차 통계를 낸다. **통과 기준: p95 ≤ 2 cm / 1°.**
이 관문을 통과하지 못하면 Phase 3은 의미가 없다.

## 8. Phase 3 — 폐루프 주행

### 팀 리드 — `aruco_navigator_node`

`nav2_msgs/action/NavigateToPose` 액션 서버. **표준 필드(목표 pose)만 사용한다.**

기존 `navigate_action_server.py`는 `goal.behavior_tree` 문자열을 모드 채널로 전용(轉用)하고
있는데(`carry`, `carry_bay`, `rotate` 등), 이는 nav2 계약 위반이다. 새 주행기는 이 함정을
반복하지 않는다.

- 경로 = `site_map_v4`가 주는 **마커 웨이포인트 시퀀스**. 구간마다 끝에서 마커로 자세 리셋
- **방위 유지 폐루프 필수** — v1에서 요 드리프트로 검출 0/5였다가, 방위 유지를 넣어 5/5가 되었다
  (`DEBUG_LOG.md` 2026-07-20 심야). 13.6 m 횡이동에 −12.8°가 누적됐고, 요각 e는 1.25 m 앞
  지면 패치를 `1.25·tan(e)` 만큼 옆으로 민다
- 홀로노믹 P 제어 (메카넘이므로 횡방향 직접 사용)

### 팔로워 — gap-hold

리드에 대한 상대 간격 유지. 기존 `gap_hold_controller.py`와 `formation_assignment` 재사용.
절대측위 불필요(카메라 대수는 Probe C가 결정).

### 마커 미검출 처리

```
예상 마커 지점을 (검출 창 폭)만큼 지나도 fix 없음
        ↓
횡방향 탐색: ±(검출 창 폭) 범위를 저속으로 1회 왕복
        ↓
그래도 없음 → 구간 ABORT, 실패 보고
```

탐색 범위를 검출 창 폭에 묶는 이유는, 그보다 크게 벗어났다면 이미 측위를 신뢰할 수 없는
상태이므로 헤매기보다 실패로 보고하는 편이 안전하기 때문이다.

GT로 몰래 대체하지 않으며, 오도메트리로 예산을 넘겨 계속 달리지 않는다.

---

## 9. Phase 4 — 두 팀 동시

입차팀(z+)과 출차팀(z−)이 같은 시간에 독립적으로 동작한다. 두 팀은 서로 반대편 통로를 쓰므로
경로가 물리적으로 분리되어 있다.

## 10. 테스트 전략

| 층 | 내용 |
|---|---|
| 단위 | 지도 생성(USD ↔ json 일치, id 유일성, 사전 범위), **z 반전 매핑**, 경로 생성 |
| probe | A / B / C 리포트 JSON + GUI 관찰 |
| 관문 | **M5 정확도**: p95 ≤ 2 cm / 1° |
| E2E | ① 도크 → 인계장 정렬 ② 인계장 → A3 통로 주행 ③ 두 팀 동시 |

**모든 E2E는 `markers_used > 0`과 `gt_used_for_control == False`를 합격 조건에 포함한다.**
마커를 쓰지 않고 통과하는 것이 원천적으로 불가능해야 한다.

### 수용 기준

- 정렬 오차 **2 cm / 1°** 이내
- 두 시나리오(도크→인계장, 인계장→A3) 모두 통과
- 두 팀 동시 실행에서 상호 간섭으로 인한 실패 없음

---

## 11. 운영 주의사항

- 러너는 `--odom={gt,wheel}` 플래그를 갖는다. 기본은 `wheel`. `gt`는 비교·디버깅 전용이며
  이 값으로 E2E를 통과시킬 수 없다(10절 합격 조건).
- Isaac은 종료가 걸려 **좀비 프로세스**가 남을 수 있다. 실행 전후로 반드시 확인·정리한다.
- USD에 **절대경로를 굽지 않는다.** 팀 간 에셋 교환에서 전부 끊긴다.
- 환경 에셋 파일명이 계속 바뀐다(v2→v3→v4). 러너는 파일이 없으면 조용히 오작동하지 않고
  후보 목록을 출력하며 즉시 실패한다.

## 12. 단계 요약

```
Phase 0  probe A/B/C (GUI)  ──▶ 사용자 결정: 카메라 높이 / 마커 추가 / 카메라 대수
Phase 1  지도 생성 (+ 필요 시 마커 보강)
Phase 2  측위 + M5 관문 (p95 ≤ 2cm/1°)
Phase 3  폐루프 주행: 리드 NavigateToPose + 팔로워 gap-hold
Phase 4  입차·출차 두 팀 동시
```

Phase 0의 실측이 이후 단계의 수치를 정한다. 따라서 Phase 0을 먼저 만들어 GUI로 보여드리고,
그 자리에서 결정한 값으로 Phase 1 이후를 진행한다.

### 구현 계획 분할

**첫 구현 계획은 Phase 0(+ v4 러너)만 다룬다.** Phase 1~4의 구체 수치는 Phase 0 실측 결과에
의존하므로, 지금 상세 계획을 세우면 추측으로 채우게 된다. Phase 0 결과를 사용자와 함께 본 뒤
Phase 1 이후를 다시 계획한다.

첫 계획의 산출물:

1. v4 전용 러너 — 로봇 4대 배치, 휠 오도메트리 발행, `--odom={gt,wheel}`
2. `site_map_v4.py` — z 반전을 가두는 매핑 (단위 테스트 포함)
3. Probe A / B / C — `--gui` 관찰형 + JSON 리포트

## 부록 A — Phase 0 측정 결과와 결정 (2026-07-24)

Phase 0 probe 3종을 GUI 관찰형으로 구현·실행하고, 사용자가 수치를 보고 결정했다.

### 측정 결과

| Probe | 측정 | 결과 |
|---|---|---|
| A 검출 창 | 카메라 높이별 마커 검출 구간 | 0.09m → 0.70m (d 1.10~1.80) / 0.12m → 0.80m (~1.90) / 0.15m → 0.90m (~2.00). d_min 1.10 고정 |
| B 오도 드리프트 | 마커 없이 4m 주행 시 오차율 | **20.19%** (3회 bit-identical). 구간별 전진 32.6% / 횡 13.7% |
| C 렌더 부하 | 카메라 대수별 RTF | 0대 8.02 / 2대 1.55 / 4대 1.12 |

결정 규칙 `최장 무마커 구간 × 드리프트율 < 검출 창 폭 × 0.5` 적용 시, 오도메트리만으로 건널 수 있는
최대 마커 간격은 0.09m→1.73m, 0.12m→1.98m, 0.15m→2.23m. v4 실제 간격(도크→인계장 7.2m,
인계장→크로싱 6.0m, 크로싱→슬롯 5.3m)은 모두 초과 → **카메라 상향만으로는 불가, 마커 추가 필수.**

### 결정

1. **카메라 높이: 0.15m 로 상향** (런타임 override, 팀원 에셋 미수정). 검출 창 0.90m.
2. **마커 추가: Phase 1 지도 생성 시 긴 구간에 보강** (간격 ≤ 2m 목표). 좌표·ID 는 기존 체계
   (DICT_5X5_100, ID 블록, 0.25m 타일)를 이어 정한다.
3. **카메라 대수: 팀당 리드 1대 = 총 2대** (`entry_lead`, `exit_lead`). 팔로워는 gap-hold.
   RTF 4대에서도 1.12로 성능 여유는 있으나, 실로봇 구성과 일치하는 리드 전용 측위를 택했다.

### Phase 0 이 발견한 것 (다음 단계 필수 반영)

- **드리프트가 정착 프레임 수에 비단조로 민감**(2.69%~20.19%). 메카넘 롤러 10개가 이산이라
  주행 시작 시 롤러 접촉 위상이 슬립을 지배. Phase 3 주행 컨트롤러는 이 변동을 전제로 설계.
- **도크 마커 좌표 지뢰**: v4 에셋에서 도크 마커(D_IN/D_OUT)만 `aruco:position`(도크 중심 z=±2.2)과
  실제 데칼(z=±2.9)이 **0.7m 차이**. 슬롯·크로싱 등은 일치. **Phase 1 지도(marker_map)는 도크 마커에
  대해 데칼 실제 위치를 써야 한다** — `aruco:position` 을 그대로 쓰면 도크 근처 측위가 0.7m 틀어진다.
- 카메라 실제 시선은 월드 +X(로봇 스폰이 RotateX(-90)). 검출·측위 배선에서 좌표축 주의.
